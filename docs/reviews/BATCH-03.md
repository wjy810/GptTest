## 3. 三站差异与可迁移原则

| 维度     | EMBER 餐厅                           | ROAM 旅行                                    | P1XEL 街机                                                           |
| -------- | ------------------------------------ | -------------------------------------------- | -------------------------------------------------------------------- |
| 视觉重心 | 酒红、奶油白、餐盘与光影、克制衬线字 | 蓝灰山峦、日落橙、自然层次、大幅风景         | 深紫黑、荧光绿、像素插画、硬边按钮                                   |
| 内容节奏 | 氛围 → 菜品 → 餐桌故事 → 预约        | 向往 → 地点比较 → 手记 → 预算草案            | 宣言 → 游戏选择 → 即时反应 → 成绩                                    |
| 实际任务 | 筛菜并形成符合营业规则的预约摘要     | 筛选、收藏、计算预算、下载行程草案           | 完成反应回合、查看和导出个人本地成绩                                 |
| 手机组织 | 菜单与预约顺序阅读，保留食物主视觉   | 风景卡片单列，规划表单按任务下移             | 保留大面积操作区，状态信息围绕游戏区域                               |
| 状态边界 | 预约摘要只在当前页面，不提交到餐厅   | 收藏持久化；表单与草案在当前页面；价格是示例 | 收藏仅当前会话；最多 30 条成绩本地持久化；只有 REFLEX.EXE 可实际游玩 |

这三站的独立性来自内容结构、主操作和状态流。它们各自拥有导航、视觉体系和页脚，不依赖目录页面提供运行外框。

从本轮带入下一批的原则：

1. **让展示信息参与表单规则。** “周一休息”若只是页脚文字，就无法保护预约流程；地区日期也要遵循实际营业地时区。
2. **按数据实体记录生命周期。** 同站的收藏、成绩、表单可以采用不同存储方式。文档要逐项写清楚，不能用一个“支持本地保存”概括全部状态。
3. **读取损坏集合时逐项恢复。** 一个异常成员不应清空所有有效历史；当前操作也应在存储不可用时继续，并给出准确反馈。
4. **关闭窗口后按任务意图安置焦点。** 单纯查看详情应回到触发处；“去规划”是进入下一步，应把目的地和焦点一起交给表单。
5. **下载结果必须实际回读。** 有下载按钮不代表文件内容正确；以具体地点、人数和金额验证表单、摘要与文件的一致性。
6. **动效和时序逻辑分别验证。** 减少动画不应关闭游戏必要状态；计时受浏览器和输入设备影响，不包装成科学能力评估。

本轮未执行屏幕阅读器人工朗读、Safari / iOS 真机、完整色彩对比度扫描、真实餐厅预订或旅行报价接口，也未验证云端排行榜。没有这些能力的演示界面，文案和文档均不得暗示已经接入真实服务。
