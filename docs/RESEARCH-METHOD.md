# UI/UX 研究、视频拆解与知识库维护方法

目标是把广泛的灵感转化成可检索、可解释、可复现的方法。市场中的 UI/UX 案例持续变化，单次研究不能覆盖“全部设计”。本项目采用跨平台、跨风格、跨任务的代表性采样，并把方法落实为独立网站；每条来源保留访问状态，未观看的视频不写成已经分析的案例。

本轮真实访问记录见 [SOURCES.md](SOURCES.md)。本文件中的关键词和表格是**后续研究方法**，不代表已经观看、抓取或验证相应平台上的具体作品。

## 建立采样矩阵

每次研究选择至少两种不同维度，避免结果全是某一类获奖首页。

| 维度 | 候选范围 |
| --- | --- |
| 业务 | 商业 SaaS、电商、金融、教育、医疗、文化、公共服务、游戏、个人创作 |
| 风格 | 编辑排版、瑞士网格、粗野主义、极简、复古像素、玻璃、拟物、有机、实验 3D |
| 任务 | 发现内容、搜索、选择、输入、支付、学习、创作、协作、错误恢复 |
| 载体 | 网站、移动端、桌面应用、游戏 HUD、公共屏幕、视频演示 |
| 来源 | 官方文档、真实产品、设计奖项、作品社区、源码示例、视频、社交讨论 |
| 成熟度 | 概念稿、交互原型、正式产品、开源实现 |

例如“非商业 + 有机 + 内容发现”与“商业 + 瑞士网格 + 数据选择”可以共享排版原则，但实际交互约束不同。不要把吸引眼球的宣传动效直接视为可用性证据。

## 搜索路径与关键词

### B 站与中文视频平台

可从以下关键词开始，每轮加上具体任务词来缩小范围：

- `UI 设计 交互 拆解`、`网页设计 创意 动效`、`作品集 网站 复刻`
- `Figma 原型 变量 交互`、`设计系统 组件 状态`、`响应式 布局 网格`
- `粗野主义 网页`、`瑞士平面 网格 排版`、`编辑设计 网页`
- `GSAP ScrollTrigger 教程`、`Three.js 网页 交互`、`CSS 玻璃 拟物`
- `游戏 HUD UX`、`无障碍 交互设计`、`表单 错误提示 用户体验`

视频平台的搜索结果往往偏向教程和展示，不代表设计效果已被用户研究验证。先识别作者实际展示的是成品、概念动画还是教程过程，再决定怎么收录。优先保存单个视频的直接链接和具体片段时间码，搜索页只作为入口。

### YouTube 与英文资料

组合 `interaction design breakdown`、`creative developer portfolio`、`editorial website design`、`brutalist web design`、`accessible modal dialog`、`dashboard UX case study`、`motion design web` 与目标技术或任务词。优先查作者原始演示和官方教程，转载内容回溯原作者。

### 社交媒体与作品社区

Behance、Dribbble、设计师个人站、Are.na、Figma Community、Pinterest、小红书等适合发现方向。收录时至少追溯到具体作品页；记录概念稿与上线产品的区别。评论可以提供线索，不能直接当成成功率或用户偏好的统计结论。

### 文档与开源实例

官方设计规范、WAI-ARIA Authoring Practices、组件文档和开源示例用于核对语义与实现。源码能说明“如何做”，但仍需在浏览器里验证“实际显示与操作怎样”。仓库有截图或动图时也要检查对应版本，避免把历史画面误认为当前实现。

## 访问证据分层

| 级别 | 已经知道什么 | 不能据此宣称什么 |
| --- | --- | --- |
| 入口已知 | 有一个相关 URL | 内容仍在线、内容已阅读 |
| HTTP 已响应 | 服务返回了响应 | 正文正确、视觉完整、视频已观看 |
| 正文已读取 | 读到了可识别的标题与内容 | 动效、键盘和移动端行为已验证 |
| 视觉已检查 | 在某个视口观察到画面 | 所有交互与设备都正常 |
| 交互已执行 | 完成了具体操作路径 | 所有错误路径和无障碍要求都通过 |
| 视频片段已观看 | 看过明确时间区间 | 全片已观看、原产品可用性已验证 |

记录网络失败时写下实际信息，例如状态码、超时、需要登录或页面提示。不要把所有访问失败都归因为平台封禁，也不要把成功状态码当成页面内容获取成功。

## 一个视频的拆解流程

1. **确认对象。** 记录作者、标题、原始 URL、发布日期（可见时）、观看日期和语言。
2. **定位片段。** 标明起止时间，记录字幕是否自动生成；不要用自动摘要代替观察。
3. **截取状态。** 至少观察交互前、触发瞬间、过渡中、完成后。若视频只展示完成态，就明确缺少输入与失败状态。
4. **写事实。** 例如“按钮点击后卡片展开，右侧出现详情”；不要立即写“提升转化率”。
5. **写推断。** 例如“可能利用共享元素过渡维持空间连续性”；用“推测”标明未经源码确认的实现。
6. **做最小复现。** 用自有文字和图形，先复现状态变化，再调时间和视觉参数。
7. **验证差异。** 记录无法从视频推断的移动端、键盘、加载和错误行为，并补足自己的实现。

### 视频取证模板

```markdown
## 案例：<标题>
- 原始来源：<单个视频或作品的 URL>
- 作者：<作者名称 / 未提供>
- 作品性质：概念稿 / 原型 / 已上线产品 / 无法确认
- 检查日期：YYYY-MM-DD
- 观察方式：浏览器播放 / 已获授权的本地文件 / 仅查看简介
- 实际观看：00:42–01:18；02:10–02:36
- 未观看范围：其余片段
- 设备与视口：<桌面 / 手机；已知尺寸>

| 时间码 | 可见事实 | 推断与未知 | 可迁移原则 |
| --- | --- | --- | --- |
| 00:42 | <发生了什么> | <无法确认的实现> | <布局 / 状态 / 反馈> |
| 00:53 | <交互结果> | <错误状态未展示> | <可逆操作等> |

### 复刻参数
- 布局：<列数、容器、对齐>
- 排版：<字号比例、行高；未知就写估算>
- 动效：<估计时长、缓动、触发；明确估算>
- 状态：<默认、焦点、选中、加载、成功、失败>
- 自行补充：<视频未展示但实现需要的行为>
- 实现入口：<源码路径>
- 验证结果：<实际执行的检查与结论>
```

## 把观察写成知识卡片

一张卡片只解释一个主要方法，建议包含：

1. **问题：** 用户在哪一步需要帮助。
2. **原则：** 为什么这种结构可能有用。
3. **可见证据：** 来源中的具体画面、文字或执行过的行为。
4. **实施参数：** 网格、比例、时长、状态与组件语义。
5. **适用条件：** 适合什么内容、设备与用户目标。
6. **失败边界：** 哪些情况下会降低可读性或增加操作负担。
7. **复现与验证：** 最小代码入口、真实验证结果、未知事项。

坏例子：“玻璃设计很高级，适合所有后台。”

好例子：“在背景变化缓慢的媒体控制界面，用单层半透明面板建立前后关系；正文区域保留足够不透明度。对背景最亮和最暗两种状态检查对比度，并在不支持模糊时提供实色背景。”

## 评估与优先级

可以对以下各项按 0–2 分做编辑筛选，分数用于选题排序，不冒充用户研究数据：

| 项目 | 0 分 | 1 分 | 2 分 |
| --- | --- | --- | --- |
| 独特性 | 重复已有案例 | 有局部变化 | 提供新方法或场景 |
| 证据 | 只有入口 | 读到部分内容 | 已观察相关行为 |
| 可迁移性 | 依赖品牌资产 | 可抽取部分原则 | 可明确复用到其他任务 |
| 可实施性 | 关键依赖未知 | 能做简化版 | 有清楚实现与验证路径 |
| 完整性 | 仅静态画面 | 有部分状态 | 主要状态和降级清楚 |

优先做证据充足、方法不同、实现成本可控的案例；把优秀但暂时无法访问的来源放入待核验列表。

## 归属与素材处理

保留原作者、直接链接和具体借鉴点。复刻练习优先使用原创文案、CSS/SVG 图形与有明确许可的素材。不开箱搬运品牌标志、商业字体或未经许可的完整作品包。引用开源代码时保留其许可证要求，不能仅因 GitHub 可访问就推定可自由再分发。

学习结果应表达为“从案例提炼的原则 + 自己的实现与取舍”，而不是把他人完整作品换名发布。

## 持续维护

- **新增时：** 检查重复 URL，保存访问日期、证据范围和作者归属。
- **每次扩展专题：** 补齐采样矩阵中缺少的任务或平台，而不是增加同质截图。
- **定期复查：** 失效链接保留历史说明；新 URL 不覆盖旧证据，追加核验记录。
- **更新实现时：** 同步源码入口和复刻参数，区分原案例观察与自己后来添加的功能。
- **发布前：** 检查所有“已验证”“已观看”“通过”是否都有对应记录；未知事项保留为未知。

研究是否有用，最终由它能否帮助下一位开发者完成一个可运行、可解释、可验证的界面来判断。
